## 结论与小结

我把这 140 页对话和最后的运行日志串起来看了。**她现在不是单纯“模型选错”或“代码写错”中的一个问题，而是视觉任务的拆分方式、模型训练域和代码筛选策略同时存在问题。**

最明确的判断是：

1. **整体 ROS 2 调度架构有基本逻辑，问题主要集中在视觉子系统。**
2. **RapidOCR 不适合作为全图中孤立超大彩色数字的首级定位器。**
3. 后来换成 YOLO 的方向不算错，但使用了车牌、SVHN 或手写数字等**非比赛场景权重**，仍然存在严重的训练域错配。
4. 最终把货架上的纸筒识别为“8”，不是“视觉已经跑通”，而是非常典型的**错误模型 + `conf=0.15` 超低阈值 + 最大面积候选策略**共同造成的假阳性。日志里目标明明是绿色数字 1，模型却框住旁边物体并输出橙色 8，因此不能视为成功。fileciteturn7file0
5. **需要更换当前权重和视觉方案，但不建议继续盲目下载另一个现成 YOLO 模型。**最合适的方案是：

> **A4 纸/中心区域定位 → 数字前景分割 → 轻量 0–9 分类模型 → 前景颜色判断 → 多帧投票**

而不是继续在 RapidOCR、手写 YOLO、车牌 YOLO、SVHN YOLO 之间来回切换。

她把大部分功能都集中到了一个 ROS 2 节点：

```text

        ▼
ExecutionDispatcherNode
        │
```

### 这套架构的优点

- 意图入口统一，能够承接你们前面的闭集 JSON。

- 知道颜色识别和数字识别应该分开处理。

所以她的工作并不是没有框架，**主要是视觉算法不断被临时补丁拖偏了。**

# 二、任务 3 到底出了什么问题

## 1. 第一阶段：RapidOCR 的问题

最初路线是：

```text
全图 → RapidOCR 检测文字框 → 提取数字 → 选最大框 → HSV 判断颜色
```

RapidOCR 本质上是通用 OCR 流水线，需要先由文本检测模块找出“文本区域”，再由识别模块识别字符。PaddleOCR 官方文档也明确把 OCR 划分为文本检测和文本识别两个阶段。citeturn255311search24turn255311search30

这里的目标却是：

- 单个数字；
- 字符“1”只有一个主要竖笔画；
- 字号非常大；
- 颜色可能是绿色、橙色等；
- 周围不是文本行，而是复杂实验室背景。

这与普通文档、招牌、车牌中的文本区域分布差异很大。因此它可能根本不生成目标框。后面的面积比较、中心距离和字符映射只有在 OCR **先检测出框**以后才有用；如果检测阶段没有框，任何“选最大”“选中心”都救不了。

对话里连续加入：

- 多尺度放大；
- 多尺度缩小；
- CLAHE；
- 白边 padding；
- 面积权重；
- 中心距离权重；
- `I/L/T/7 → 1`；

但日志仍然显示所有尺度都没有检测到目标。fileciteturn1file0

这说明问题不在于再调一个缩放比例，而在于**首级检测器不适合该任务。**

---

## 2. OCR 代码本身又制造了假阳性

早期代码里有大量强制映射：

```python
S -> 2
O -> 0
Z -> 2
I -> 1
L -> 1
B -> 8
T -> 1
7 -> 1
```

这导致衣服上的 `SCUL`、货架标签或其他英文字符，也可能被“洗”成数字。

而且多个版本使用：

```python
if any(char.isdigit() ...):
    ...
    break
```

即发现第一个疑似数字就停止，正好重现了最开始“识别衣服文字、不看 A4 纸”的问题。

后来虽然改成面积和中心评分，但仍然有一个前提：

> OCR 必须先把真正的数字 1 检测出来。

真正目标没进入候选集时，再优秀的评分公式也无意义。

---

## 3. 第二阶段：YOLO 的思路对了一半

换成 YOLO，代表从“读取文本”转为“检测一个数字物体”，这个任务抽象比全图 OCR 更合理。

但是她先后尝试的权重包括：

- 车牌数字；
- SVHN 街景数字；
- 手写数字 HWD+；
- 网上下载的未知 ONNX 模型。

这些模型虽然类别可能都是 0–9，但训练图像与比赛图像不同：

| 模型训练域 | 比赛目标 |
|---|---|
| 手写数字 | 标准印刷体 |
| 街景门牌 | 白色 A4 纸 |
| 车牌字符 | 无车牌边框的大号单字符 |
| 多个小数字 | 一个超大彩色数字 |
| 自然背景数字 | 单色粗字体 |

因此，**README 中写着“数字检测”不等于它适合你们的数字。**

Ultralytics 官方也把自定义数据训练作为将检测模型适配具体实际场景的核心步骤，而不是仅更换一个通用预训练权重。citeturn255311search16turn255311search18

---

## 4. 最终为什么把纸筒认成“8”

最终日志是：

```text
YOLO 瞬间锁定目标: '8'
面积: 115256.2
颜色判定结果: 橙
```

但输入图里真正目标是中央白纸上的绿色数字 1。

这个错误由三部分组成：

### 模型训练域不匹配

手写数字模型对弯曲、圆形笔画更敏感，而标准印刷体 1 可能只表现为一条规则的绿色竖形区域。旁边纸筒、线轴的圆孔反而更接近训练数据里“8”的局部形状。

### 置信度阈值过低

代码把阈值降到了：

```python
conf = 0.15
```

15% 的相似度也允许输出，复杂货架环境中必然会产生大量假阳性。文件中的异常栈也明确显示推理使用了 `conf=0.15`。fileciteturn7file2

### 最大面积策略放大了错误

代码不是选择“最可信”的候选，而是从输出框中选面积最大的：

```python
if area > max_area:
    best_box = ...
```

一旦纸筒被低置信度误检成 8，因为它面积大，就会压过其他候选。

所以这是：

> **模型域错配为根因，低置信度和最大面积策略进一步放大错误。**

不是 YOLO 模型结构本身不好，也不是简单换 YOLOv8、YOLO11 或更新版本就能解决。

# 三、对话中 AI 给出的分析有哪些明显问题

## 1. 经常把猜测说成确定结论

例如反复声称：

- “字太大超过感受野”；
- “缩小到 0.25 一定识别”；
- “YOLO 绝对能解决”；
- “视觉问题已经彻底解决”；
- “换回 OCR 一定精准”。

这些都没有通过离线对照实验、置信度、检测框和测试集验证。

尤其模型把纸筒识别成 8 后，AI 先说“视觉识别问题已经彻底解决”，但下一页又承认目标本应是 1。这种判断明显错误。fileciteturn7file0

## 2. 在 OCR 和 YOLO 之间反复横跳

实际过程是：

```text
OCR
→ OCR 加面积
→ OCR 加 CLAHE
→ OCR 放大
→ OCR 缩小
→ OCR 中心评分
→ YOLO 车牌模型
→ YOLO 手写模型
→ YOLO ONNX
→ 又建议回到原始 OCR
```

最后重新给出的 OCR 代码仍然有：

```python
找到第一个疑似字符就 break
```

相当于把最开始识别衣服文字的问题重新引入。

## 3. 没有建立固定测试集

每次换算法都用现场一两张图测试，没有：

- 固定的 0–9 测试图片；
- 不同颜色；
- 不同距离；
- 不同倾斜角；
- 不同光照；
- 背景有无人物；
- 识别准确率、漏检率、误检率；
- 单帧耗时。

因此无法判断修改到底是进步还是退步。

# 四、当前最合适的视觉方案

## 推荐方案：结构化视觉 + 小型分类器

这是最适合“白色 A4 纸上一个彩色数字”的路线：

```text
深度相机 RGB
    │
    ├── 旋转 180°
    │
    ├── 截取中央有效区域
    │
    ├── 检测白色 A4 纸四边形
    │
    ├── 透视矫正为正视图
    │
    ├── 从白纸中分割高饱和度/非白色数字
    │
    ├── 提取最大连通区域
    │
    ├── 归一化为 64×64
    │
    ├── 0–9 轻量分类器
    │
    ├── 从数字前景像素计算 HSV 颜色
    │
    └── 连续 3～5 帧投票后播报
```

OpenCV 官方提供的阈值化、轮廓、面积、中心点和透视变换正适合完成纸张与数字前景定位。citeturn255311search1turn255311search9turn255311search14

### 数字模型建议

不要再使用通用目标检测权重，使用一个小型十分类模型：

- 简单三层或四层 CNN；
- MobileNetV3-Small；
- 轻量 ResNet；
- 最终导出 ONNX。

它只负责回答：

```text
这张已经裁好的数字图是 0、1、2……还是 9？
```

不需要同时负责在整个实验室里寻找数字，任务会简单很多。

### 数据应来自真实机器人相机

训练数据至少要覆盖：

- 比赛实际字体；
- 0–9；
- 所有规定颜色；
- 真实相机翻转后的画面；
- 远近变化；
- 轻度旋转和透视；
- 明暗变化；
- 手持纸张；
- 货架、衣服、人员等实际背景。

可以用电脑生成大量合成 A4 数字图，但必须混入真实机器人相机图片进行微调和独立测试。

# 五、什么时候才应该用自定义 YOLO

只有以下情况更适合 YOLO：

- A4 纸可能出现在画面任意位置；
- 纸张经常被遮挡；
- 不保证是白色纸；
- 画面里同时出现多个数字；
- 数字本身很小；
- 还需要检测其他物体。

这时可以训练一个**你们自己的数字检测模型**，类别为 0–9，训练图片直接使用机器人第一视角。

关键不是“YOLO 哪一代”，而是：

```text
训练集是否和比赛图像一致
```

直接使用手写、车牌、街景数字权重，继续出现误检并不意外。

# 六、RapidOCR 是否完全不能用

不需要删除，但应改变位置。

正确用法是：

```text
先找到 A4 纸并透视矫正
        ↓
只把裁好的纸张或数字区域交给 OCR 识别
```

也就是绕过最不稳定的“全图文本检测”，把 OCR 作为备用识别器，而不是让它在整个仓库背景里找一个孤立数字。通用 OCR 本身就是检测和识别两级结构，先裁 ROI 再识别，比全图直接扫更符合它的工作方式。citeturn255311search28turn255311search32

---

# 七、颜色识别代码也需要调整

当前方法是在整个检测框内统计：

```python
红、橙、黄、绿、蓝、黑、白各有多少像素
```

问题是检测框内通常还包含大量白纸，可能把白色判为主色；如果框错到了纸筒，就会正确识别纸筒的橙色，但这个颜色与目标数字没有关系。

应改为：

1. 先排除低饱和度白纸背景；
2. 只保留数字连通域；
3. 对数字前景像素统计 HSV；
4. 使用有效像素比例，而不是固定“至少 20 个像素”；
5. 过滤高光、阴影和过暗像素。

即：

```text
颜色应该从数字前景中识别，
不能从整个目标框中识别。
```

# 八、现有代码除模型外还有几个重要问题

## 1. 一个节点承担过多功能

`ExecutionDispatcherNode` 同时负责：

- TTS；
- 表情；
- 动作；
- 导航；
- OCR；
- YOLO；
- RGBD；
- TF；
- 抓取坐标；
- 麦克风状态。

任何一个 Python 依赖冲突都会让整个执行节点无法启动。对话里安装 Ultralytics 后升级 NumPy，导致 ROS/cv_bridge 相关模块崩溃，就是这种强耦合的结果。fileciteturn6file3

建议拆成：

```text
execution_dispatcher_node
vision_task3_node
vision_task4_node
tts_audio_node
```

至少把深度学习推理从执行调度节点分离。

## 2. RGB 和深度没有时间同步

当前只保存：

```python
self.latest_depth_image
```

然后在下一张 RGB 图到达时直接使用。

这可能让 RGB 和深度来自不同时间，尤其机器人、目标或持纸人移动时，像素和深度会错位。应使用 ROS 2 `message_filters` 的近似时间同步，或至少记录时间戳并限制允许的时间差。

## 3. “TF 会再次翻转图像”的说法不准确

TF 负责的是三维坐标系变换，不会自动替你翻转二维像素。

180° 旋转后进行：

```python
u_raw = width - 1 - u_rotated
v_raw = height - 1 - v_rotated
```

这个二维映射本身是合理的，但必须同时保证：

- RGB 与深度分辨率一致或已经配准；
- 深度图没有被另外旋转；
- CameraInfo 对应原始图像；
- 使用的是同一时刻的数据；
- TF 使用正确的 optical frame。

## 4. TTS 完成回调存在状态竞争

`_finish_tts()` 中无条件：

```python
callback(None)
self.set_mic_status(True)
```

任务 4 原本关闭麦克风后启动导航，但 TTS 完成时又会自动重新打开麦克风。动作任务中也可能在动作真正结束之前重新开放监听。

麦克风状态应该由状态机决定，不能由所有 TTS 完成函数统一开启。

## 5. 安装依赖的方式不稳定

文件中出现了：

- NumPy 1.x/2.x ABI 冲突；
- OpenCV 版本冲突；
- Ultralytics 自动安装 ONNX；
- ONNX 文件损坏；
- Ctrl+C 后 ROS context 重复 shutdown；
- Sherpa-onnx 推理崩溃。

这些属于部署环境问题，不是数字识别模型准确率问题。fileciteturn7file1turn7file2

更稳妥的方式是：

- 在开发机训练；
- 导出固定 ONNX；
- 机器人只安装固定版本 `onnxruntime`；
- 使用独立虚拟环境或独立视觉节点；
- 保存版本锁定文件；
- 禁止 Ultralytics 运行时自动更新依赖。

# 九、最终判断

| 问题 | 判断 |
|---|---|
| RapidOCR 是否选错 | **作为全图首级检测器不合适** |
| YOLO 思路是否错误 | **不完全错误，但现成权重选错** |
| 最终误识别是模型问题吗 | **主要是训练域不匹配** |
| 是否也有代码问题 | **有，而且明显放大了误检** |
| 换更大的 YOLO 是否能解决 | **不能保证，版本不是核心** |
| 是否需要重新训练 | 使用 YOLO 时，**需要真实场景微调** |
| 最推荐方案 | **A4/中央 ROI 定位 + 前景分割 + 小型数字分类器** |
| 颜色怎么识别 | **只统计数字前景像素** |
| RapidOCR 还能否保留 | **可作为裁剪后的备用识别器** |
| 任务 4 是否已经可靠 | **还没有，RGB-depth 同步和状态控制需修正** |

一句话概括：

> **她的调度主框架可以保留，但视觉部分需要停止“给模型打补丁”的方式。当前根因是把一个结构高度明确的比赛任务，当成了通用 OCR/通用目标检测问题。最稳的解决方案不是继续寻找神奇预训练模型，而是利用“中央位置、白纸、单个数字、固定颜色集合”这些先验条件，把任务拆成定位、分割、分类和颜色判断四个简单模块。**



## 结论

**有现成模型。你们现在最合适的不是再找一个 YOLO 数字检测模型，而是改用：**

> **OpenCV 截取 A4 纸/画面中央区域 + `en_PP-OCRv4_mobile_rec` 纯文字识别模型**

这是目前时间紧、CPU 真机部署、无需训练情况下，我最推荐的方案。

它与之前 RapidOCR 的关键区别是：

```text
原方案：
整张复杂画面
  → OCR 检测器先找文字框
  → 识别数字
  ✘ 卡在“找不到绿色数字1”

推荐方案：
画面中央/A4纸区域
  → OpenCV直接裁剪数字
  → 纯识别模型判断0～9
  ✔ 不再让OCR负责找框
```

你们遇到的核心问题正是：**RapidOCR 的文本检测模块没有把孤立的彩色大号“1”当成文字区域**，后面的识别模型根本没有机会运行。

---

# 推荐顺序

| 推荐度 | 现成模型/方案                         | 适合你们的程度 | 说明                        |
| --- | ------------------------------- | ------: | ------------------------- |
| 🥇  | `en_PP-OCRv4_mobile_rec`        |  **最高** | 小、快、支持英文和数字，只运行识别，不运行文本检测 |
| 🥈  | Tesseract 5，`PSM 10`            |       高 | 专门按“单个字符”识别，可限制只能输出0～9    |
| 🥉  | `microsoft/trocr-small-printed` |       中 | 印刷文字识别能力较强，但模型较大，CPU部署更重  |
| 不推荐 | 手写数字YOLO、SVHN YOLO、车牌数字YOLO     |       低 | 与A4纸彩色印刷数字的图像域不匹配         |

# 第一选择：PP-OCRv4 纯识别模型

## 模型名称

```text
en_PP-OCRv4_mobile_rec
```

PaddleOCR 官方将它定义为轻量英文文字识别模型，明确支持英文和数字识别；模型约 **7.5 MB**，官方给出的CPU推理时间约为毫秒级，适合你们没有GPU的机器人。([PaddlePaddle][1])

这里一定要注意：

> **只调用 Text Recognition，不使用 Text Detection。**

不要再使用这种全流程：

```python
res, _ = self.ocr_engine(full_image)
```

而应当先把数字裁剪出来，再把小图送入识别器。

## 实际流程

```text
RGBD图像
  ↓
旋转180°
  ↓
截取画面中央60%区域
  ↓
检测白色A4纸，或直接使用固定中央ROI
  ↓
根据饱和度提取彩色数字
  ↓
裁剪数字并添加白边
  ↓
统一缩放
  ↓
en_PP-OCRv4_mobile_rec
  ↓
只接受0～9
```

这种做法能避开当前最致命的问题：**模型不再需要从衣服、货架和纸筒中寻找文字。**

PaddleOCR目前也支持将文字识别模块单独运行，并可选择 ONNX Runtime 推理后端。([PaddlePaddle][1])

---

# 第二选择：Tesseract 5 单字符模式

Tesseract 官方提供：

```text
--psm 10
```

含义是：

> 将输入图像视为单个字符。

还可以增加数字白名单：

```text
tessedit_char_whitelist=0123456789
```

Tesseract官方文档明确说明，`PSM 10` 用于单字符识别，并支持通过字符白名单限制输出范围。([Tesseract OCR][2])

Python调用可以这样设置：

```python
config = (
    "--oem 1 "
    "--psm 10 "
    "-c tessedit_char_whitelist=0123456789 "
    "-c load_system_dawg=0 "
    "-c load_freq_dawg=0"
)

text = pytesseract.image_to_string(
    digit_crop,
    config=config
).strip()
```

### Tesseract适合做什么

它很适合当第二识别器：

```text
PP-OCR结果 = 1
Tesseract结果 = 1
→ 高可信度，播报

两个结果不同
→ 再读取下一帧，不立即播报
```

这样不需要训练，却能明显降低纸筒被识别成“8”之类的假阳性。

---

# 第三选择：Microsoft TrOCR Small Printed

模型名称：

```text
microsoft/trocr-small-printed
```

这是针对印刷文字进行微调的端到端识别模型，官方模型卡说明它适用于**已经裁剪好的单行文字图像**。([Hugging Face][3])

但它有约 **6140万参数**，相对于7.5 MB的PaddleOCR移动模型明显更重。([Hugging Face][3])

你们机器人没有GPU，而且执行节点还同时运行：

* ROS 2；
* Sherpa-onnx TTS；
* 图像订阅；
* 深度图处理；
* TF；
* 导航和动作接口。

因此 TrOCR 可以测试，但不应作为第一选择，容易增加内存占用、启动时间和依赖冲突。

---

# 不建议继续找的模型

以下类型即使名字写着“数字检测”，也不建议继续用：

### 1. MNIST或手写数字模型

训练对象是手写数字，你们是标准印刷字体，尤其数字“1”的形态差异非常大。

### 2. SVHN街景数字模型

训练对象通常是门牌、街景、小型连续数字，颜色、背景、尺度都与A4纸单数字不同。

### 3. 车牌数字YOLO

模型往往依赖车牌矩形、字符排列和车牌纹理。离开车牌后，货架圆孔、纸筒、按钮等都可能被误认为数字。

### 4. 通用YOLO模型

标准COCO预训练权重没有数字0～9类别，无法直接识别你们的数字。

# 最推荐的应急组合

## 数字定位

不使用模型，直接利用比赛规则：

```text
数字大概率位于机器人正前方
A4纸大概率位于画面中央
背景是白色
数字是高饱和度彩色区域
```

先截取中央区域，例如：

```python
h, w = img.shape[:2]

roi = img[
    int(h * 0.15):int(h * 0.90),
    int(w * 0.20):int(w * 0.80)
]
```

再在 HSV 中排除白纸：

```python
hsv = cv2.cvtColor(roi, cv2.COLOR_BGR2HSV)

# 彩色数字一般饱和度较高，白纸饱和度接近0
mask = cv2.inRange(
    hsv,
    np.array([0, 45, 35]),
    np.array([179, 255, 255])
)
```

找到最大连通域后，只把这个区域交给识别器。

## 数字识别

```text
主识别器：en_PP-OCRv4_mobile_rec
备用识别器：Tesseract PSM 10
```

## 颜色识别

直接从已经得到的数字前景 mask 中计算 HSV，不再统计整个检测框：

```text
只统计数字像素
不统计白纸
不统计手
不统计纸筒
```

## 输出条件

```text
连续3帧中至少2帧数字一致
连续3帧中至少2帧颜色一致
才进行TTS播报
```

# 最终选择

现在直接按这个组合实施最稳妥：

```text
中央ROI
  → HSV提取彩色最大连通域
  → en_PP-OCRv4_mobile_rec
  → Tesseract PSM 10复核
  → 前景HSV识别颜色
  → 3帧投票
```

**不需要训练，不需要YOLO，不需要让OCR在整张复杂画面中寻找文字框，也不会再通过降低置信度强行把纸筒判成数字。**
